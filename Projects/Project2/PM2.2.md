# Project Milestone 2.2: Development Sprint II

This project milestone will focus on the development and maintenance of your Project 2 system.

### Maintenance

> This section is vague on purpose to facilitate different team/project expectations. You must create a fork of the original Project 1 repository and make contributions to your team's version of the codebase for your project throughout the second half of the semester. There is nothing to submit on Canvas for these activities, however the following will be evaluated on your overall Project 2 GitHub repository at the end of the project:

**Requirements & Design**

For each enhancement, use the [agent template](https://github.com/CS3704-VT/agent-template) to produce and commit one requirements artifact (user story with Given/When/Then criteria, or use case) under `docs/requirements/`, and one design artifact (ADR, class/sequence diagram, data model, or implementation sketch) under `docs/design/`. The IDs of generated artifacts (e.g., `US-###`, `UC-###`, `REQ-###`, `ADR-####`) can be referenced for future milestones and agentic development tasks. If your team decides not to use AI for this project, you may produce the artifacts manually.

**Project Management**

You must use GitHub Projects to manage project tasks. Tasks must be assigned to individual team members and using columns to track progress for each sprint.


**Testing**

Generate unit tests for any function(s) implemented for PM2.1 (at least one unit test per function, or if applicable---at least one integration test incorporating multiple functions working together). You may use AI to generate the tests, and must adhere to the course AI policy (comment tests generated by AI with prompts and/or provide log, etc.). The tests should be added to your repository.

**Code Review**

For major code contributions, please submit a pull request to the repository (for simple changes, pushing directly to the repo is ok). The code may be generated by a teammate or by AI, adhering to the class and team AI policies. In the pull request, please add an appropriate title, comment, etc. A peer code review must be conducted for each pull request to your repository. A team member should review a segment of code submitted by another teammate (AI- or human-generated, but not their own PR) and provide a brief review describing the following items:

* Overview: General comment summarizing the review.

* Correctness: Does the code work for the intended purpose?

* Quality: Is it readable and understandable?

* Maintainability: Does it follow normal coding and style conventions?

* AI-Specific Concerns: If AI was used, explain what issues were found in AI-generated code and potential lessons learned about relying on AI for implementation.

* Recommendation: A final outcome for the PR: merge as is, close, return for changes, etc.

### Black Box Test Plan

A test plan is a detailed document that outlines test cases for a given software system. Black box test plans are documents that use plain language for stakeholders to follow to verify the program. For this milestone, you must create a black box test plan with at least ten unique black box test cases with the required test case information (you must use the template in the Lecture Slides). Your test cases should also relate to the acceptance criteria of your project requirements and constraints.

> For this submission, the actual results column can be blank. However, by the end of the semester you will need to complete the plan to show your system works as expected.
